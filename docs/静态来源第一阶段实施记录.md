## 已实现

- 新增供应商档案 `partner`，区分 GROUP / THIRD_PARTY，与商家及历史酒店集团业务键分开。
- 新增独立来源快照、单一确认映射、主来源发布记录与修改前后审计。
- 内部流程：登记供应商 → 同步来源快照 → 查询来源资料/人工核实候选 → 确认平台酒店 → 显式发布。
- 选源使用已确认的集团优先；无集团时按稳定来源ID选第三方。多个集团来源阻止发布，避免任意覆盖。
- 发布只更新展示字段，保留平台主键、历史酒店业务键、房型关联、上下线状态和取消政策；不更新任何价库、供应订单或历史订单。
- 缺失可选字段不清空现有展示字段，审计记录本次覆盖字段；尚未启用跨来源自动补齐或字段锁定。
- 同步旧版本拒绝；相同版本同内容幂等，不同内容冲突；已确认来源城市/地址变化阻止覆盖，留待后续映射纠错流程。
- 酒店缓存改为事务提交后失效；Redis清理失败会记录错误，持久化失效重试属于后续可靠性阶段。
- 既有候选算法加入名称二元组、地址门牌冲突、电话/品牌证据、显式坐标系与有效范围校验；缺失坐标不加分，跨坐标系不计算距离；结果仍为人工候选。

## 上线前置条件

1. 对运行库执行只读结构核对，确认不存在与新 `partner` 同名但结构不同的旧表；脚本不会自动覆盖同名旧表。
2. 在目标 `ota_cloud` 数据库单独执行 `init-sql/005-hotel-static-source.sql`。本次开发没有连接或修改运行数据库。
3. 部署后按环境配置 `HOTEL_SOURCES_ENABLED=true` 和非空 `HOTEL_SOURCES_INTERNAL_TOKEN`。默认关闭，不要求已有数据库立即升级。
4. 内部接口位于 `/internal/hotel-sources`，不属于Gateway现有 `/api/hotel/**` 转发路径；仍需限制直连网络访问。

## 内部接口

全部接口要求 `X-OTA-Internal-Token`；缺失密钥配置时全部拒绝。

| 方法/路径 | 用途 |
| --- | --- |
| POST `/internal/hotel-sources/partners` | 登记code/name/partnerType，不覆盖既有身份 |
| POST `/internal/hotel-sources` | 同步partnerCode/sourceHotelId/sourceVersion/data，返回来源ID |
| GET `/internal/hotel-sources/{id}` | 查询来源快照与确认目标 |
| POST `/internal/hotel-sources/{id}/confirm` | 人工确认hotelId，记录可信内部调用方提供的operator |
| POST `/internal/hotel-sources/hotels/{hotelId}/publish` | 显式发布，提交operator，返回所选来源 |

`data` 的hotelTitle/cityCode/address为必填，行政编码须已归一；坐标保留bdLat/bdLog及gdLat/gdLog两组，不隐式转换。groupCode/brandCode记录静态归属，第一阶段不改历史hotel.partner_code/brand_code，待房型映射迁移后统一。

现有admin候选入口与新增确认映射暂分开：旧候选用于人工核实，新hotel_source.mapped_hotel_id才参与本次主来源发布；不得以旧表任意CONFIRMED记录自动迁移新来源身份。
