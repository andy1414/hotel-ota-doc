## 十、未关闭问题

### 复核-01：冲突事件的读取排序不能保证到达顺序（P1，阻断）

位置：`ota-supplier/.../booking/SupplierBookingStore.java` 的 `mergeCancel`/`enqueue`；`SupplierCallbackDeliveryJob.java:29–38`；`SupplierBookingMapper.xml:42–48`。完整 Java 目录为 `ota-supplier/src/main/java/com/ota/cloud/supplier/booking/`，XML 位于 `ota-supplier/src/main/resources/mapper/`。

当前修复：明确取消结果不会再被 UNKNOWN 或相反结果覆盖，供应侧保存先到事实；冲突时先入队原结果，再入队相反结果，以 `ORDER BY next_attempt_at,id` 排序。

剩余触发路径：原结果为拒绝，第一条拒绝事件转发失败，Job 调用 `retry` 将其延期后仍继续处理后面的 CANCELLED；或两个实例分别 claim 两条不同事件。现有 claim 只有事件级租约，没有同订单前序 ACK 门槛。相反结果因此可以先进入订单收件箱。订单按到达顺序处理，先到 CANCELLED 可立即归还配额、进入退款，再到拒绝只能将状态置为人工复核，无法撤回已发生的副作用。这违反“原拒绝保留且不释放、不退款”的端到端要求。

现有竞态用例验证 SQL 排序后的事件列表，订单测试直接按预设顺序送入 inbox，未验证 Job 的网络失败和多实例交错。该问题为源码可达路径，本轮未新增运行时复现，不应描述为已执行 HTTP 复现。

关闭要求：使订单能够识别权威原事实与冲突证据，或建立持久化的同订单事件顺序和前序确认门槛；不能只排序或加固定延迟。验证拒绝事件首次 HTTP 失败、两实例并发、租约过期恢复、同步 RPC 与回调交错；任何情况下相反证据不能触发与原拒绝冲突的库存退款动作。

### 复核-02：通知故障脚本可在未验证故障订单时输出 PASS（P2，验收阻断）

位置：`scripts/booking-flow-smoke.py:193–209`。

脚本将 `ntf_id` 加入错误 ACK 集合，固定等待两秒后移除；没有断言曾发出错误 ACK，也没有查询其是否被识别为失败/待重试。最终等待只检查 `completed` 中的两笔正常取消订单，不包含 `ntf_id`。因此即使该故障订单从未收到通知，脚本也可能输出 PASS 与 `notificationProtectedOrderId`。固定两秒也可能短于调度间隔，导致错误 ACK 根本未发生。

此外，脚本没有执行复核包要求的重试耗尽及人工重放，不应将“已补齐链路-05”作为完整场景通过结论。

关闭要求：用事件及条件等待证明错误 ACK 已实际发生且未被记成功；恢复 ACK 后等待同一故障订单的正确事件真正送达。增加重试耗尽状态、人工重放调用及审计的断言；在任一必需行为未发生时超时失败，不能继续输出 PASS。
