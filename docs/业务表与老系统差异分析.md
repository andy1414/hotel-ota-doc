核查日期：2026-10-29。范围：本仓库初始化/增量 SQL、当前工作区代码与 `/Users/fuxinwei/work/db` 导出文件。未连接数据库，未执行迁移；下文“当前表”指仓库声明的结构，不代表运行库实际结构。

后续业务口径已确认：核心主体为平台、供应商、渠道，不引入独立商家租户；partner 为集团或第三方供应来源；静态数据以 api_hotel.txt 为参考、集团来源优先。详细目标设计见 [平台、供应商、渠道业务优化需求设计](superpowers/specs/2026-10-29-平台供应商渠道业务优化需求设计.md)。本文保留初次核查记录，其中商家定位及渠道方向的待定项以新设计为准。

- `hotel_order1.txt` 的 `hotel_order.room_price` 是价库参考，含价格码、入住人数价格、早餐和取消/预订规则。
- `hoa_channel_data_range.sql` 只声明规则 1～4；`api_hotel.txt:216` 声明规则 1～6、状态 0～3。两者存在版本差异，不能按文件名认定哪份代表最后上线模型。
- `partner.sql` 当前内容是 `hotel_order.partner` 的 INSERT，未提供 `partner_basic` DDL。`002-merchant.sql` 关于来源 `partner_basic` 的说明无法由该文件证明。`hoa_partner.sql` 则明确描述集团、分润、结算配置，不能直接等同商家租户。
- DDL 只能证明字段和注释约定；系数执行顺序、渠道方向、分润公式等还须以老系统上线代码及业务确认补证。

## 二、优先修正的逻辑

### 1. 价库缺少价格计划与来源选择维度

来源：`hotel_order1.txt:1729` 的 `room_price`，字段 `partner_code/room_type_code/sale_code/date`，以及 `sale_price1～5`、`breakfast`、`cancel_rule`、`reserve_rule` 等。

当前：`init-sql/001-init.sql:180` 的 `inventory_price_stock` 唯一键只有 `hotel_id/room_type_code/biz_date`；有来源字段，但来源不参与唯一键或选价条件，也没有 `sale_code`。`InventoryPriceStockMapper.xml` 查询同样只按酒店、房型、日期。

影响：一个房型同一天不能保存多个价格计划或多个独立来源的报价。订单保存的 `sale_code` 不能证明实际查到的价格属于该计划。

调整方向：先定义报价唯一身份，再将价格计划和来源选择贯穿查询、缓存、订单和库存操作。不同计划是否共享房量必须单独建模，不能简单加唯一键后让每个计划各自拥有完整库存。

### 2. 下单价格与渠道展示价格未统一

当前：`OrderService.loadAndValidatePrices:390` 调用价库只传酒店、房型和入住区间，没有传 `channelCode/saleCode`；`ChannelPricingService` 已支持渠道系数。`buildInitOrder:425` 保存 saleCode，但总价在此前按所查基础价汇总。

影响：渠道报价与最终下单金额存在不一致风险；价格码也只落在订单字段，尚未成为实际选价条件。

调整方向：使用同一报价契约完成展示与下单验价，保存逐日价格、渠道、计划、来源及规则版本快照；服务端决定金额和供应路由。

### 3. 价格码规则的集团范围被丢弃

来源：`api_hotel.txt:216` 的 `hoa_channel_data_range.partner_code` 注释明确覆盖规则 1/2/3/4。

当前：`ChannelDataRangeService.normalizeByRuleType:144` 对规则 4 清空 partnerCode；`validateRule` 只要求 saleCode。`previewEffectiveCoe:69` 虽传集团参数，存储时却已丢弃集团范围。

影响：需要按集团区分的同名价格码无法正确配置；正常带集团的预览与保存后的规则还可能无法匹配。

调整方向：核实老系统规则 4 的匹配实现，按集团+价格码保留维度；兼容现有全局价格码规则时需显式定义范围，不能静默改变旧数据含义。

补充：`sumEnabledCoeByRuleType` 在条件为 null 时直接省略过滤；预览接口应校验各维度，避免缺参变成跨范围累加。规则唯一键含多个 nullable 字段，应用“先查重再写入”不能避免并发重复，应增加数据库层有效唯一约束。

### 4. 订单状态与履约、支付、取消需要拆清

来源：`order.sql` 与 `api_hotel.txt:318` 的 status 表达下单/取消结果，check_in_status 表达预订、入住、离店；balance_type 包含 PP/FG/PKG。

当前：订单主线以 INIT/WAIT_PAY/PAID 等状态推进；`buildInitOrder` 固定支付类型并在 INIT 时将 checkInStatus 置 0。当前取消逻辑主要覆盖未支付订单，已支付订单要求走退款。

调整方向：保留新系统状态编码，明确支付、供应预订、入住、取消、退款和结算的状态边界；预订成功不得仅由已支付推断。FG/PKG 若纳入迁移范围，需要独立业务流程。

### 5. 预订规则与取消政策没有形成订单快照

来源：`api_hotel.txt:533` 的 product、`:405` 的 order_product，以及 room_price 的规则字段。老表包含预订/入住时间窗、周控、提前天数、连住限制、取消政策和阶梯规则；order_product 为订单保留商品快照。

当前：初始化 SQL 未声明对应商品、订单商品快照表；已核查的下单价库校验仅检查日期记录数量、售价非空和库存数量。

调整方向：下单前执行适用规则并落快照；取消按下单时政策计算。退款、取消记录、状态日志分别参考 `order_cancel/order_refund/order_status_change_log`，不直接照搬旧表结构。

## 三、业务模型缺口

| 领域 | 老系统依据 | 当前差异与建议 |
| --- | --- | --- |
| 入住资料 | order.person/person_name/person_mobile/guests | 当前订单表缺少完整联系人、入住人快照；DTO 有 linkMobile，但主表无对应字段。按供应接口需要补齐并保护敏感数据。 |
| 财务对账 | order 的佣金/结算字段；order_refund/order_supplementary；bill/bill_details | 当前订单主要保存 total_price。现有远端状态对比不能替代财务结算；后续补成交成本、分润、结算和调整流水。 |
| 商家归属 | 当前新增 merchant 模型，旧集团表不能直接替代 | `buildInitOrder` 未设置 merchantId，Mapper 却显式插入该字段；数据库默认 0 不会替显式 NULL 生效。应先定义归属来源，再在可信服务端赋值。 |
| 外部单号 | order.out_order_no/up_channel_id | 当前 out_order_no 初始化为空，需明确来源渠道+外部订单号幂等键，且区分渠道来单和向渠道推单。 |
| 路由 | order_route_rule.sql | 老系统显式区分流量来源渠道与 hoa_channel。不能仅按“上游/下游”注释重命名推导业务方向；需结合上线调用核查。 |

## 四、建议实施顺序

1. 确定集团、商家、流量来源渠道、供应商、分销渠道的身份关系及业务编号映射。
2. 定义报价/价格计划/共享库存模型，修正下单验价和价格码规则集团维度。
3. 补齐订单归属、入住资料、逐日价格与政策快照。
4. 扩展供应确认、取消、退款、入住和结算流程；补持久化审计与补偿记录。
5. 提供独立增量迁移、存量回填及相应回归测试，不能仅修改初始化脚本。

验证重点：同酒店同房型多计划、多来源报价；不同集团同名价格码；渠道展示与下单金额一致；共享库存不重复放量；商家归属；政策变更后老订单仍按快照执行。

## 五、实施前需确定的业务口径

- 本期是否覆盖老系统的直连酒店全流程，以及 FG 现付、PKG 包价、退款和结算？
- 商家是独立租户、集团经营主体还是渠道经营主体？与酒店/供应商是一对多还是多对多？
- 多价格计划是否共享房量；来源报价是实时供应可用量还是平台独立配额？
- 渠道模型是否同时包含来源渠道来单与主动向分销渠道推单？

以上问题不能仅从 DDL 确定。当前交付为差异核查，不执行有歧义的业务模型迁移。
