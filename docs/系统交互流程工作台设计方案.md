## 一、设计目标

把现有展示页改为可操作的“系统流程工作台”。使用者可以从整个系统进入某项业务，再下钻到一次验签、一次数据库写入、一次库存转移，观察操作前后发生了什么，也能切换异常条件观察处理分支。

默认打开即可离线演示，不要求先启动后端或登录。演示对象是平台接入多个集团/第三方供应商，再向多个渠道供货的当前业务模型。

主要用户：需要了解业务的同事、评审技术方案的开发人员、介绍项目的讲解者。首屏先展示能运行的业务流程；技术细节按需展开。

## 二、现有页面问题与改造原则

基于本次源码核对：

| 现状 | 影响 | 改造 |
| --- | --- | --- |
| 大幅介绍、指标、架构和证据组成长页 | 操作区域分散，需滚动寻找上下文 | 固定工作台，画布、步骤和状态同屏 |
| 六个按钮推进单一 currentStep | 只能看到大步骤，无法看步骤内部 | 场景 → 子流程 → 原子事件三级 |
| 架构节点按步骤高亮 | 无法查看请求方向、等待和返回 | 可点击节点/边、流动事件、同步与异步泳道 |
| READY/WAIT_PAY/PAID/CANCELLED 简化状态 | 无法表达确认、支付、取消和退款独立演进 | 多实体状态面板和事件回放 |
| 商家模块、JWT 下单与旧 Kafka 支付主链路仍展示 | 与当前平台/供应商/渠道交易模型不一致 | 以当前交易契约为依据，归档逻辑不进入默认业务图 |
| 写死金额、延迟和成功证据 | 无法判断模拟、真实响应或实际内部链路 | 逐条显示数据来源及证据等级 |
| App.tsx 同时承担页面、请求和模拟逻辑 | 难以扩展更多微流程 | 拆分流程定义、执行器、数据适配器与可视化组件 |

保留 React、TypeScript、Vite、Lucide，以及已有浅色基调。重新组织交互与数据模型，不继续往长页追加展示区块。

- 左侧约 220px：业务目录、场景选择、已运行记录。切换场景提示是否保留当前运行；默认保留到本地运行列表。
- 中央自适应：业务图或时序图。右上角提供缩放、适应画布、返回上层及图例。
- 右侧约 340px：当前选择的节点、边或事件。默认显示业务解释，展开“技术详情”后才看 API、表和字段。

- 全景默认收起基础设施；展开后显示各服务实际使用关系，不把 Redis、Kafka 等连接到所有业务步骤。

视觉方向：浅灰画布、白色内容面、深色文字。蓝色表示调用，青色表示明确完成，橙色表示等待/未知，红色表示失败，紫色仅标记人工复核。节点同时显示文字和图标，不能只靠颜色区别。

## 四、三级交互

### 第一级：系统全景

按“上游供应 → 平台 → 下游渠道”展示业务关系；交易播放时可沿请求方向反向经过同一拓扑。节点包括集团、第三方、静态来源处理、酒店主数据、报价配额、订单编排、供应适配、渠道分发、网关。平台管理与基础设施为辅助层。

点击业务域进入子流程；点击服务显示职责、端口、相关接口和参与场景。选中一个运行时，只突出实际参与的服务，其余淡化。服务运行状态与业务运行状态分开，不把动画节点当成服务健康证明。

### 第二级：业务子流程

以泳道展示渠道、网关/渠道服务、订单、库存、供应服务、上游和本地持久化。小流程节点可点击、折叠、展开；分支条件写在连线上。

例如“占用配额”展开为：读取报价 → 校验渠道和有效期 → 核对冻结价格与计划 → 锁定所属配额 → 写入占用记录 → 提交本地事务 → 返回。具体表名及操作顺序由当前代码核对后录入，未经确认不标为真实源码对应。

### 第三级：原子事件

选中事件显示：执行主体、输入条件、动作、输出、状态前后值、持久化记录、幂等键、失败处理及后续可选动作。

示例：“异步受理”执行后，供应为 PENDING_CONFIRM，库存仍受保护，订单不能标为已确认；面板同时解释“受理不等于确认”。只有这个事件发生时才更新状态与对应动画。

每个子流程提供“只运行这一段”：自动载入清楚标注的前置演示状态，不能让使用者为了看取消拒绝反复点击前面的全部流程。

| 业务域 | 场景与可运行的小流程 | 核心可视化 |
| --- | --- | --- |
| 静态接入 | 集团静态首次接入、第三方接入、字段标准化 | 来源快照与平台主数据分列 |
| 酒店归一 | 名称/地址模糊匹配、多个候选、人工确认/拒绝 | 名称、地址、城市等维度及候选依据；分值为演示值时明确标注 |
| 主来源选择 | 仅第三方、集团加入、切换发布来源 | 平台酒店 ID 不变；静态、价库、履约来源三个独立身份 |
| 房型映射 | 上游房型绑定平台房型、拒绝/撤销映射 | 多来源映射和报价可用性变化 |
| 报价配额 | 渠道权限、价格计划、报价冻结、共享池占用 | 渠道价格与平台内部采购信息分视图；逐日数量 |
| 即时确认 | 创建、占用、持久化提交意图、明确供应确认 | 订单、供应、库存、付款四条状态并行 |
| 异步确认 | 供应受理、等待回调、验签、收件箱、应用结果 | 等待区、事件去重、回调路径 |
| 付款策略 | BEFORE_SUBMIT、AFTER_CONFIRM | 相同场景对照两种付款时机及起算点 |
| 幂等 | 相同外部单号重试、内容冲突、重复回调 | 请求次数与实际外部操作次数分开显示 |
| 未知恢复 | 提交超时、供应已受理、按原请求查证 | UNKNOWN 保留配额；不生成新供应请求 |
| 取消退款 | 未提交取消、已确认取消、退款待处理/成功/失败 | 取消、库存归还与退款独立发生 |
| 取消拒绝 | 明确拒绝、相同请求重试、换号被拒 | 预订保持有效、配额不归还、不退款 |
| 冲突事实 | 原事实/冲突乱序、前序依赖、查证恢复 | 两类事件区别，冲突进入复核，不直接执行成功副作用 |
| 渠道通知 | 持久化接收、错误 ACK、重试、DEAD、人工重放 | 尝试次数、下次重试、事件 ACK、审计 |
| 版本替换 | 旧版本失败、新版本到达、SUPERSEDED | 旧事件退出投递，稳定新版本继续处理 |
| 对账 | 本地/远端一致、不一致、远端不可用 | 差异字段及可查证依据，不把 UNKNOWN 判一致 |

默认推荐“异步确认全流程”，旁边提供“即时确认”“取消被拒”“通知重放”快捷入口。场景多但不一次全部挤到主画布。

## 六、完整交互示例：异步确认

使用者选择“异步确认 / AFTER_CONFIRM / 1 间 / 1 晚”。点击播放：

1. 渠道发送签名报价请求，网关转发；点击验签节点，可单步查看时间戳、nonce 去重和渠道绑定。页面不展示签名密钥。
2. 生成演示报价，冻结平台酒店/房型、名称、价格、政策和供货身份。右侧可查看“当前静态信息”与“报价快照”差异。
3. 创建订单，检查外部单号幂等，占用共享配额。底部逐日可用从 10 变 9，冻结从 0 变 1。
4. 订单持久化供应提交意图，再向供应服务发送固定请求号。点击数据库事件，展示本地事务已提交后才发生网络调用。
5. 上游受理，进入等待。播放停在“等待外部结果”，操作区出现“确认成功”“明确失败”“超时未知”。
6. 选择“确认成功”，回调沿独立虚线进入验签、收件箱、去重和结果应用；冻结转已订。首次明确确认后开始付款倒计时。
7. 使用者点击“TEST 付款成功”，资金事实与供应事实同时满足，订单确认。操作按钮保留 TEST 标识。
8. 订单通知先到渠道收件箱，再投递外部渠道；这两段分别显示 ACK，不能合成一次“通知成功”。
9. 点击“重复发送此回调”，请求计数增加，库存与订单事实不重复变更。

在第 5 步选“超时未知”时，配额仍冻结受保护，时间轴显示查证；点击“上游实际已确认”后按原请求号恢复。不能用界面等待超时直接演示为失败释放。

## 七、播放与故障交互规则

- 播放/暂停/下一步/上一步/重置、0.5×/1×/2×/4×、时间轴定位。
- 自动播放在等待外部事件或分支选择处暂停；暂停时画面和模拟时钟均停止。
- 上一步、拖动时间轴只重建演示或回放视图，不撤销真实订单。真实模式不能提供会再次发送请求的回退操作。
- 回到历史步骤后改变分支会建立新运行分支，旧事件记录保留，避免把两种结果混在一条链上。
- 故障从对应节点插入：提交超时、回调重复/乱序、取消拒绝、错误 ACK、租约过期。未到相关步骤时显示触发条件，不允许任意组合造成不可解释状态。
- “推进 30 秒”“跳到下次重试”用于模拟时钟，不让讲解者真的等待退避时间。真实耗时与动画时长分别标注。
- 并发演示提供双工作线程泳道和可控闸门，可先后放行两个 worker，观察领取、租约和前序依赖；不使用随机定时制造偶发结果。
- 对照模式可将同一初始条件下的两个运行并排：即时/异步、付款前/付款后、正常 ACK/错误 ACK；状态变化按逻辑事件对齐。

## 八、信息面板与动效

右侧详情分为“说明、状态、请求、数据、依据”。普通展示默认说明和状态，技术讲解再展开其余内容。

请求显示调用方/接收方、方法、路径、同步/异步、请求号、事件号和脱敏载荷。数据显示表、主键及本步写入，不直接运行 SQL。依据区链接源码或文档，并标注核对日期；点击源码链接需由本地展示环境支持，不能假设浏览器可直接读取任意文件。

节点状态包括未执行、运行中、等待、完成、失败、复核；“未执行”不能呈现绿色健康点。实线表示请求/返回，虚线表示异步事件，事务范围以边框标识，等待点显示可操作分支。

动效只解释事件：调用沿边移动、事务提交一次脉冲、状态差异短暂高亮、配额在可用/冻结/已订三栏间移动。减少动态效果模式下改为静态高亮和文字；任何动画结束回调都不能驱动业务状态。

## 九、数据来源与真实性

| 模式 | 能做什么 | 必须明确的边界 |
| --- | --- | --- |
| 离线演示（默认） | 完整单步、时间旅行、故障、并发、对照 | 合成数据和模拟时间，不能写成真实链路或真实测试证据 |
| 证据回放 | 导入脱敏 JSON 事件，按记录回放 | 仅展示采集到的事实，缺失步骤标为未采集，不补造内部成功 |
| 测试环境操作 | 通过受控服务调用真实测试接口并查询结果 | 请求成功只证明该接口响应；未采集的内部行为显示未知 |

真实模式默认只读；交易动作由明确按钮触发，标明目标测试环境与影响。浏览器不保存供应回调密钥、渠道 HMAC 密钥、内部 token、支付签名密钥或默认管理员密码。若要驱动 HMAC 测试渠道，通过本机/测试环境的受控服务代理处理，浏览器只拿演示会话；这部分需要新增服务能力，不能声称现有项目已具备。

真实接口失败不得悄悄回退模拟成功；可显式新开离线运行。测试报告必须附来源、时间、版本和执行范围，删除当前写死的“100% 对应”“真实支付完全吻合”等泛化证明。

## 十、实现结构

保留当前目录作为承载项目，按以下职责拆分：

```text
src/
  app/                 工作台布局、路由、运行管理
  components/          画布、泳道、详情、时间轴、状态条
  domain/              实体状态、事件类型、业务不变量
  scenarios/           场景目录、初始条件、分支和微流程定义
  engine/              纯事件归约器、模拟时钟、调度、历史重建
  adapters/            离线、证据文件、测试环境适配
  data/                演示样例、源码/接口依据映射
```

核心记录：运行包含场景、参数、数据来源、事件流和分支父节点；事件包含稳定 ID、逻辑序号、模拟时间、执行主体、关联实体、因果事件、状态差异、事务范围及证据引用。展示上的 Trace 与真实服务 Trace 分开命名，不能随机生成后冒称后端 TraceId。

业务状态由纯归约器应用事件得到，组件只负责展示和发送意图；使用独立模拟时钟。可保存周期检查点加事件流用于时间轴重建，重播不重复副作用。图、时序、状态条和日志共享同一事件源，不能各自维护一套演示状态。

画布首版可用 React + SVG 实现固定泳道和有限节点，满足点击、折叠、平移缩放；不为装饰引入图形库。若确定需要任意拖拽布局和大规模图编辑，再选型并核对依赖。此文不要求用户编辑架构图。

业务不变量至少包括：未知不释放受保护配额；拒绝取消不退款；冲突证据不执行取消成功；重复事件不重复计数；静态切换不改历史身份；支付与确认分开；已替代通知不当作已送达；共享配额按天守恒。

## 十二、实施顺序与验收

第一批先做可体验的闭环：工作台布局、三级下钻、统一事件执行器、异步确认/即时确认/取消拒绝/通知重放四个场景；这些场景需能离线完整演示，不能只做会动的架构图。

第二批补全静态来源、酒店匹配、房型映射、共享配额、未知恢复和冲突事实；加入局部运行、双 worker 调度及运行对照。

第三批加入脱敏证据导入与只读测试查询；受控真实交易操作待服务代理及身份边界明确后接入，不作为首版体验的前置条件。

验收必须实际运行并检查 1440×900、1280×800、390×844：
