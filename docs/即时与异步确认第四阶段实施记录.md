# 即时与异步确认第四阶段实施记录

日期：2026-10-30。落实用户明确的INSTANT即时确认、ASYNC异步确认要求。本批增加报价关联履约事实与配额保护；平台订单持久化、真实供应调用、渠道认证和通知尚未交付。

## 1. 模式与快照

- 价格计划新增必填confirmation，包含mode与maxConfirmationMinutes；报价快照固定保存该配置，渠道视图明确返回模式及确认时限。
- maxConfirmationMinutes由合同配置，当前技术校验范围1～10080分钟，不是平台默认业务承诺。
- INSTANT：正常供应调用应得到明确成功/失败；仅受理、超时或含糊结果进入UNKNOWN，不能改成ASYNC或视作失败。
- ASYNC：先受理则PENDING_CONFIRM，后续依据回调或查单的明确结果推进；很快确认也仍保留原ASYNC模式。
- 老计划JSON缺少confirmation时拒绝新报价，需要明确配置并递增版本。历史报价仍可查询，但缺少模式的报价不能开始新履约；不批量推断或回填模式。

## 2. 供应提交与配额保护

1. 先按报价凭证占用配额，绑定平台订单ID。
2. 调用fulfillment/begin持久化供应请求号，校验来源/授权仍有效，登记SUBMITTING与确认截止时间。
3. 只有begin成功后，可信供应适配层才能真正向供应商发出请求。begin的重复调用只返回已有事实，不是重发供应订单的授权；响应丢失时先查证请求号。
4. begin之后配额受保护，原30分钟到期不自动释放；SUBMITTING/PENDING_CONFIRM/UNKNOWN/REVIEW_REQUIRED均阻止直接释放。
5. 供应明确CONFIRMED才核销本地配额；明确FAILED才释放。支付事实仍独立，不由本接口模拟资金成功或退款完成。
6. 确认时限到达只变为UNKNOWN并记录超时事件和告警日志，需后续查单或人工处理，不能仅因超时判失败。

本地book入口不再把一笔普通FROZEN报价直接核销；它只兼容已BOOKED的幂等读取。新核销必须由经核验的供应确认事件推进。

## 3. 供应结果收敛

| 输入结果 | 行为 |
| --- | --- |
| ASYNC受理，且未过确认时限 | PENDING_CONFIRM，保持FROZEN |
| INSTANT仅受理、任何模式结果未知、超时后仍仅受理 | UNKNOWN，保持配额，不改确认模式 |
| 明确确认成功 | CONFIRMED，本地配额核销为BOOKED；原30分钟已过但受保护时仍可按事实核销 |
| 明确失败 | FAILED，释放原订单配额；不等同支付退款完成 |
| 已确认后迟到受理/未知事件 | 记录事件，不回退终态 |
| 已确认后明确失败、已失败后明确确认、确认单号相互矛盾 | REVIEW_REQUIRED，保留当前配额事实并人工核对，不自动重新分配或退回已核销库存 |

首版明确确认要求supplierOrderNo；供应协议若只提供其他类型确认凭据，需在适配设计中明确，不得用单纯受理号冒充最终确认。

- 所有报告须匹配渠道、平台订单号和已登记供应请求号。
- expectedVersion保护并发状态更新；供应事件按requestNo+eventId幂等。
- 同事件编号、相同业务内容重试不重复执行，即使重试携带更新后的expectedVersion；相同编号不同业务内容明确冲突。
- 系统事件使用保留前缀，外部报告不能覆盖系统确认超时事件。
- 状态、配额变更与事件在同一本地事务提交；数据库失败时调用方必须保留原结果并可靠重试，不能把接口失败当作供应失败。独立收件箱与平台订单Outbox后续再接。

## 4. 内部接口

继续使用 `/internal/rates` 与X-OTA-Internal-Token；以下是可信适配层接口，不是供应商可直接调用的公网回调。

| 方法/路径 | 请求关键字段 |
| --- | --- |
| POST `/quotes/{id}/fulfillment/begin` | channelCode/orderId/requestNo |
| POST `/quotes/{id}/fulfillment/outcome` | channelCode/orderId/requestNo/eventId/expectedVersion/outcome/supplierOrderNo/reason |
| GET `/quotes/{id}` | 返回confirmationMode、maxConfirmationMinutes、fulfillmentState、fulfillmentVersion、confirmationDueAt等 |

outcome只接受ACCEPTED/CONFIRMED/FAILED/UNKNOWN。供应回调验签、查询协议转换、受理号独立建模和请求分发由后续适配层完成，当前没有自动发出真实供应请求。

## 5. 迁移与兼容

- 新增 `init-sql/009-quote-confirmation.sql`，增加履约事实和事件表。
- 开启当前报价功能前须完成005～009迁移；仍默认关闭，不执行远端迁移。
- 计划登记新增必填confirmation，已有调用方需要修改；旧报价和配额流水不改写、不重新解释为供应商成功。
- 第三批的30分钟释放仅适用于未提交供应的占用；存在活跃履约事实时，扫描SQL及事务内检查共同阻止释放。
- 真实异步下单仍需接通供应查单/回调、待确认取消及人工处理流程后才能开放；受保护的UNKNOWN不能无人处理地无限积压。

## 6. 验证范围与剩余工作

H2事务回归验证：模式展示、旧计划拒绝、异步受理保护、超时仅转未知、迟到确认、即时受理不等于确认、失败释放幂等、事件改写拒绝、终态矛盾隔离、错误请求号/版本拦截及禁止直接核销。

未执行真实MySQL迁移或供应商联调。支付时点、待确认取消承诺、确认失败后的退款等仍按供应合同和渠道协议确定，本批没有替用户作默认业务决定。
