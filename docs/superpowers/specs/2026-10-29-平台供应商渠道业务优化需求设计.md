## 2. 目标与范围

### 2.1 已确认的业务口径

1. 当前只有平台、供应商、渠道三类核心主体，不存在独立商家租户。
2. `partner` 表示上游供应商或数据来源，可以是集团，也可以是第三方。
3. 静态数据字段优先参考 `/Users/fuxinwei/work/db/api_hotel.txt`。
4. 酒店静态信息可来自集团或第三方；同一家酒店存在集团静态数据时以集团为主，没有集团数据时使用第三方。
5. 同一家酒店的判断需要结合名称、地址等多个维度进行模糊匹配，不能依赖单一名称相等。
6. 平台整合供应商资源，再向多个渠道供货。
7. 下单分为即时确认和异步确认两种模式；供应商受理、资金支付、平台配额核销均不能代替预订确认。

### 2.2 本次优化目标

- 建立稳定的平台酒店身份，将各来源酒店关联到平台酒店。
- 将静态数据来源、价库来源、实际履约供应商分别记录，避免混用。
- 同一家酒店支持多个供应商、多个房型映射及多个价格计划。
- 渠道可售范围、报价、下单金额及履约来源保持一致且可追溯。
- 修正订单权限、状态并发、事件重试和缓存一致性问题。
- 将现有 merchant 能力中有用的账号、权限、对账功能迁入正确主体；不直接将 merchant 改名为 partner。

### 2.3 分期边界

| 范围 | 本期定位 |
| --- | --- |
| 主体模型、静态归一、报价闭环、渠道订单、供应履约 | 核心交付范围 |
| 预付 PP、取消政策快照、取消及退款记录 | 核心模型与流程范围；真实资金执行取决于支付接入 |
| 现付 FG、包价 PKG、小时房 | 保留扩展身份；未完成规则与适配前不对渠道开放 |
| 财务核对、成交成本、退款金额与调整记录 | 本期保存必要事实，不等同完整清结算系统 |
| 完整账单、打款、发票、多币种换汇 | 后续专项需求 |
| 自动跨酒店替换、跨供应商拼接一笔订单 | 本期不支持 |

## 4. 主体、编号与服务职责

### 4.1 主体关系

- **平台**：拥有统一酒店、统一房型、来源映射、供货规则和订单编排能力。
- **供应商 partner**：具有静态同步、价库查询、预订、查单、取消等一项或多项能力，分别配置开关。
- **渠道 channel**：获取平台可售酒店和报价，向平台下单，接收确认、取消等通知。
- **酒店集团 group 与品牌 brand**：酒店经营归属属性，不直接作为供应商 ID。集团可通过集团直连供应商供货，也可通过第三方供货。
- **平台管理员账号**：平台操作人员身份。终端入住人/渠道会员是订单参与者，不新增核心经营主体。

### 4.2 编号语义

| 标识 | 语义与约束 |
| --- | --- |
| `partner_id/partner_code` | 供应商主键/稳定业务编码；不表示平台酒店归属 |
| `partner_type` | GROUP 集团、THIRD_PARTY 第三方；不能替代每条来源数据的可信等级 |
| `group_code/brand_code` | 酒店集团/品牌属性；第三方不清楚时允许未知，禁止填第三方编码冒充集团 |
| `hotel_id` | 平台酒店主键，建立后保持稳定 |
| `source_hotel_id` | 供应商原始酒店编号，字符串原样保留；与 partner 联合定位 |
| `room_type_id` | 平台房型主键 |
| `source_room_type_code` | 来源酒店下的原始房型编号 |
| `sale_code` | 供应商作用域内的价格计划编号，不保证跨供应商唯一 |
| `channel_id/channel_code` | 下游渠道身份；接口认证后由服务端确定 |

历史 hotel.partner_code 原来可能代表集团归属，迁移时不得直接批量改解释为供应商。需要建立字段映射，保留集团信息并单独关联来源供应商。

### 4.3 服务边界

| 服务 | 目标职责 |
| --- | --- |
| `ota-hotel` | 来源静态快照、平台酒店/房型、匹配与主来源投影 |
| `ota-supplier` | 供应商适配、静态与价库拉取、预订/查单/取消协议转换 |
| `ota-inventory` | 标准报价、价格计划、配额、渠道计价与报价校验 |
| `ota-channel` | 渠道认证接入、商品/报价协议转换、渠道来单、结果通知 |
| `ota-order` | 订单、履约、取消/退款编排、快照、幂等和补偿 |

## 5. 酒店静态数据模型

### 5.1 三层存储

1. **来源层**：每个供应商独立保存原始酒店、房型快照、来源时间和同步结果。
2. **归一层**：维护平台酒店、平台房型及确认的来源映射。
3. **展示层**：按来源优先级投影对外酒店信息，字段可追溯。

不得直接用新来源覆盖唯一一份 hotel 记录后丢失旧来源。来源同步失败、来源下架、平台酒店下架是不同事件。

### 5.2 建议数据对象

以下是目标逻辑模型；实际表名及复用现有表的方案在实施设计中确定。

| 对象 | 关键字段 | 唯一性/约束 |
| --- | --- | --- |
| 供应商 `partner` | 编码、名称、类型、启用状态、静态/价库/预订能力、适配器、凭据引用 | 编码唯一；凭据不进入业务响应 |
| 来源酒店 `hotel_source` | partner、source_hotel_id、原始/标准化名称地址、集团品牌、原始及转换坐标、城市、电话、图片、来源更新时间、同步时间、数据版本、上下线状态、原始报文引用 | `(partner_id, source_hotel_id)` 唯一 |
| 平台酒店 `hotel` | 平台 ID、规范名称、集团品牌、行政区、地址、标准坐标、电话、展示属性、主来源、字段来源、发布状态、版本 | ID 稳定；名称地址不做身份唯一键 |
| 酒店映射 `hotel_source_mapping` | 来源酒店、平台酒店、候选/确认/拒绝/解除状态、评分、评分版本、证据、确认方式/人员/时间、拒绝原因 | 同一来源酒店同时最多一个有效确认映射 |
| 匹配候选 `hotel_match_candidate` | 来源酒店、候选平台酒店、各维得分、冲突项、算法版本、处理状态 | 相同来源/目标/算法版本避免重复生成 |
| 来源房型 `room_type_source` | 来源酒店、来源房型码、名称、面积、床型、窗户、入住人数、图片、有效状态、版本 | 来源酒店下房型码唯一 |
| 平台房型 `room_type` | 平台酒店、规范名称、床型/人数/窗户/面积、展示来源、发布状态 | ID 稳定，不按名称唯一 |
| 房型映射 `room_type_mapping` | 来源房型、平台房型、确认状态、证据、版本 | 来源房型同时最多一个有效平台房型 |
| 来源变更审计 | 对象、变更前后、操作原因、人员、时间、关联任务 | 历史可追踪 |

来源字段参考 api_hotel.hotel/room_type；版本、评分、字段来源、映射审核等为本次新增设计。历史 `third_id` 可保留兼容输出，但新映射以结构化关系为准。

### 5.3 主来源选择与字段合成

按“映射已确认且未隔离”筛选来源，集团直接提供的有效静态数据优先于第三方。

| 情况 | 行为 |
| --- | --- |
| 只有有效第三方数据 | 选择配置优先级最高的第三方作为主来源 |
| 已用第三方，后来集团匹配确认 | 保持平台酒店 ID，切换静态主来源并发布新版本 |
| 多个集团来源相互冲突 | 进入审核，保留当前已发布版本，不按最近更新时间强制覆盖 |
| 集团某字段缺失 | 建议由已确认第三方补齐非冲突展示字段，并记录字段来源；此建议待确认 |
| 集团同步暂时失败或数据过期 | 标记质量告警；不因一次失败自动降级并覆盖全部展示信息 |
| 主来源停用/撤销 | 经明确规则或人工审核切换；保留历史版本和原因 |

平台人工维护字段增加“锁定”标识；锁定字段不被自动同步覆盖。来源状态变化不能直接改变平台人工发布状态。

同一平台酒店使用集团静态信息，不影响渠道购买该酒店的第三方报价。静态优先级不参与供应库存的直接替换。

## 6. 酒店匹配与人工审核

### 6.1 数据标准化

- 名称：保留原始值；另存全半角、空格、标点、常见品牌别名规范化结果。
- 区分品牌词、店名词、地标和分店限定词；不得删掉机场店、火车站店等关键区别词。
- 地址：拆解行政区、道路、门牌、楼栋、楼层；保留缺失及解析失败标记。
- 城市：维护不同来源行政区映射，不能直接比较不同体系的 city_code。
- 坐标：保存坐标体系与原值，距离计算前转换为同一坐标系；禁止混算高德、百度坐标。
- 电话：规范区号、分机及多个号码；缺失不视为匹配，连锁统一客服电话只作为弱证据。

### 6.2 候选召回与综合判定

1. 已确认的来源映射优先复用；来源重大变化触发重审，不直接更换平台酒店。
2. 按标准城市/地理邻域、名称关键词、地址关键片段或电话建立多路候选召回，避免全表两两比较。
3. 对候选计算名称相似度、地址相似度、地理距离、电话、集团品牌及分店标识一致性。
4. 缺失字段标为未知，不按相同处理；不能仅对剩余一个维度归一化得到高置信度。
5. 城市、门牌、分店标识等严重冲突作为阻断或强扣分，输出明确理由。

初版评分建议：名称 30%、地址 30%、距离 25%、电话 10%、品牌/集团 5%。这是待标注样本校准的初值，不代表已验证算法。

初版决策阈值建议：总分不低于 0.92，至少两个独立位置/实体证据成立、无阻断冲突且第一二候选差不低于 0.08，才具备自动关联资格；0.75～0.92 或候选接近进入审核；更低保留不匹配。首批上线自动关联开关默认关闭，评分用于推荐，标注验收后再开放。

来源过少、无候选时可以生成待发布平台酒店，但不得直接对外发布；防止候选召回不足造成大量重复酒店。

### 6.3 审核操作

- 查看原始信息、标准化结果、各维得分、冲突项、地图位置和已有映射。
- 支持确认关联、拒绝候选、创建新平台酒店、解除关联、合并与拆分纠错。
- 拒绝结果保留为负样本，数据或算法版本变化前不反复推荐相同候选。
- 合并保留原 ID 的别名/重定向；历史订单引用及快照不得改写。
- 有活跃订单或报价时，解除映射/合并采用版本切换和停发新报价，不能重定向未完成履约目标。
- 关键操作审计，批量合并先预览影响，再执行；可撤销映射和重新发布历史投影。

### 6.4 房型匹配

先确认酒店映射，再匹配其房型；跨酒店房型不得关联。名称只作候选，床型、入住人数、窗户、面积等决定是否可视作同一售卖房型。单早/双早、可取消/不可取消属于价格计划权益，不能仅因此合并或拆分静态房型。证据不足的来源房型独立保留，审核前不参与跨来源比价。

## 7. 多来源报价与库存

### 7.1 报价身份与价格计划

报价必须关联：平台酒店/房型、来源酒店/房型、供应商、供应商账户或合同作用域、价格计划、入住日期、人数/房间数、支付类型、币种及政策版本。

| 对象 | 核心字段与约束 |
| --- | --- |
| 价格计划 `rate_plan` | 来源房型、sale_code、合同作用域、人数口径、早餐、支付类型、税费/服务费口径、取消与预订规则、有效期、状态、版本 |
| 每日报价 `rate_price_daily` | 计划 ID、日期、人数价格、供货价、展示价口径、币种、有效截止、来源版本；唯一键包含计划、日期及必要人数维度 |
| 库存池 `inventory_pool` | 来源作用域、库存模式、供应商共享池编码、来源房型、日期、容量/配额、冻结、已订、版本 |
| 计划库存关联 | 计划、库存池、作用日期；多个计划可引用同一库存池 |
| 预订占用记录 | 订单、库存池、日期、数量、占用/释放/核销状态、操作幂等键、过期时间 |

老系统 room_price.stock 只是可卖库存，不能直接当成 total 后持续覆盖本地冻结。必须区分两种模式：

- **平台独立配额**：平台维护 total/available/frozen/booked，按库存池执行本地原子变更。
- **供应实时库存**：来源库存是有时效的可用量快照，最终以供应预检/预订为准；本地占用仅作并发控制，不能声称锁住了供应真实房量。

同来源多计划是否共享库存按供应契约配置；未知时禁止复制房量视作独立库存。不同供应商报价不得直接累加为可承诺房量。

### 7.2 查询与报价凭证

1. 认证渠道，校验酒店/房型已发布且该渠道可售。
2. 获取所有已确认映射、已启用且满足政策的供应报价。
3. 校验入住每一天完整覆盖，排除过期、混币种及人数不符报价。
4. 按渠道规则计算售价，保留供应成本与规则明细供平台查看。
5. 按配置返回多个供货选项或默认推荐项；不将不同权益简单按最低价合并。
6. 生成不可篡改的报价凭证 `quote_id`，保存关联身份、逐日金额、政策版本、总价、渠道、有效期。

一笔订单一期固定一个供应商/计划覆盖完整入住区间，不跨供应商拼夜。相同平台房型下权益不同的方案分别展示。报价有效期建议默认 5 分钟，可按供应商调整；凭证有效不等于库存承诺。

## 8. 渠道供货、范围与价格规则

### 8.1 渠道身份与可售范围

- 渠道是销售侧身份，来源渠道编码必须从已认证调用主体取得。
- 可售判断独立于价格计算，默认未授权不可售；匹配到加价系数不能被当作已授权。
- 酒店发布、来源映射、供应商能力、计划状态、渠道授权、合同有效期均通过才可售。
- 渠道停用立即阻止新报价/新单，已存在订单仍可按权限查询、取消及接收通知。
- 支持集团、品牌、酒店、供应商、价格计划维度授权；显式拒绝优先于允许。规则按明确范围匹配，参数缺失不解释为全部。

### 8.2 加价规则

沿用 api_hotel.hoa_channel_data_range 的规则编号表达，但增加明确的供应商范围与平台对象映射：

| 规则编号 | 规则范围 | 必填业务维度 |
| --- | --- | --- |
| 1 | 供应商级加价 | 渠道、供应商；与旧“集团码”通过映射迁移 |
| 2 | 品牌级加价 | 渠道、供应商、品牌 |
| 3 | 酒店级加价 | 渠道、供应商、酒店 |
| 4 | 价格计划级加价 | 渠道、供应商、价格码/计划；禁止丢弃供应商维度 |
| 5 | 渠道级加价 | 渠道，不产生可售授权 |
| 6 | 酒店与价格计划级加价 | 渠道、供应商、酒店、价格码/计划 |

以上为兼容编号后的目标语义，不直接覆盖旧数据：旧 partner_code 表示集团的规则，应按迁移映射决定落供应商范围还是另建集团范围规则；不明确的进入人工处理。

建议保留各层有效系数累加，最终售价按“明确的供应基准价 × (1 + 累加系数)”计算。旧供货价是否已含佣金/税费必须配置，不得重复加价。每晚按币种精度舍入后乘间数，再汇总；规则快照包含原价、各项系数、舍入与金额明细。

报价依赖异常时不得静默按零加价成交。可使用仍有效的已发布规则版本，否则返回报价暂不可用。价格上下限、负系数及最低毛利为配置项，未配置前禁止产生负售价。

规则具备草稿/待验证/启用/停用状态；不把老状态 2/3 强行转换成启用。数据库必须防止并发重复规则；规则发布后以版本切换并失效关联缓存。

## 9. 渠道订单与供应履约

### 9.1 订单创建

#### 9.1.1 两种确认模式

| 模式 | 业务含义 | 创建接口的结果 |
| --- | --- | --- |
| 即时确认 `INSTANT` | 正常情况下供应商在本次下单调用内给出确定的预订成功/失败结果 | 确认成功才返回CONFIRMED；明确拒绝返回FAILED；超时或含糊结果返回UNKNOWN/处理中，不能伪装成确定失败 |
| 异步确认 `ASYNC` | 供应商先受理请求，后续通过回调或查单给出最终结果 | 受理后返回PENDING_CONFIRM，携带平台订单号及可用的供应受理号；最终确认/拒绝再更新订单并通知渠道 |

确认模式为供应合同/价格计划能力，由平台配置并在报价、渠道展示和订单快照中保存；具体配置粒度属于建议设计，须按实际供应接口落实。不得让客户端任意指定模式或把接口耗时直接当作模式。即时确认调用超时是结果未知，不自动改变订单原定确认模式；异步订单也可能很快收到确认。

异步计划还应声明预计确认时间及最长查证时间，渠道明确展示“待确认”，不能对外承诺已订成功。确认时限只触发查证、告警与协商取消，不直接证明供应商没有接单。

#### 9.1.2 共用创建流程

请求包含报价凭证、渠道外部订单号、入住资料及联系信息；客户端不决定履约供应商、最终金额或任意渠道身份。

1. 验证渠道权限和请求签名/重放保护。
2. 以 `(channel_id, out_order_no)` 幂等；相同单号不同核心内容返回冲突，不创建第二单。
3. 校验报价归属、有效期、映射版本与政策，执行供应预检；价格变化返回明确需重新报价的结果。
4. 保存平台订单、逐日价格、入住资料、政策与供应身份快照。
5. 按库存模式占用配额或调用供应预占；持久化每一步结果及未知状态。
6. 推进预付支付与供应确认；通过可靠事件通知渠道。

异步模式第6步先进入PENDING_CONFIRM，保存受理号、请求幂等号、确认截止时间及查单进度；即时模式根据本次确定结果推进。供应单号可能在受理时即生成，单号非空不能作为确认成功判据。

#### 9.1.3 回调、查单与异常收敛

- 供应回调须验签、校验供应商身份及请求/订单归属；回调和主动查单走同一套状态转换和审计逻辑。
- 支持先收到回调、后收到下单响应；先落平台订单和履约请求记录，再发出外部调用，避免无法关联早到的回调。
- 重复或乱序结果按请求号、事件ID及状态条件处理；不能将已确认覆盖为待确认，也不能将已取消订单因迟到确认直接恢复售卖。
- 供应明确失败后记录失败原因，按支付事实触发释放配额、关单或退款；失败与退款完成分别记录。
- 待确认超时、响应丢失和查单暂时无结果不自动当作失败；继续查证或进入人工处理，禁止未经查证重下或换供。
- 待确认期间收到取消请求时，记录取消意图并向供应商查证/取消；不直接宣告取消成功，也不提前释放仍可能被供应商占用的配额。
- 取消过程中迟到确认须进入取消补偿/人工处理，最终向渠道通知实际结果，而不是丢弃供应确认事件。
- 支付时点、供应确认时点及本地配额核销时点分别编排。异步待确认时间不得直接套用当前报价池30分钟自动释放；接入前必须支持与订单协调的保留/续期/释放机制，避免释放后又收到有效确认。

供应调用超时先按业务请求号查单，禁止未经查证就切换供应商重下。替换供应报价需确认旧请求确定失败/已取消、权益兼容和渠道价格约定，并生成新的履约尝试；一期默认人工处理，不自动换供。

### 9.2 订单数据与快照

| 对象 | 必须保存的事实 |
| --- | --- |
| 订单主表 | 平台单号、渠道、渠道外部单号、选定供应商、平台酒店/房型、入住区间、数量、币种、成交总价、聚合状态、版本 |
| 履约尝试 | 供应商及来源酒店/房型、供应价格码、请求幂等号、预占号、供应单号、调用结果、未知状态、重试及查证信息 |
| 确认模式快照 | INSTANT/ASYNC、预计/最长确认时间、受理号、确认截止时间、最后查证时间及最终确认/拒绝依据 |
| 每日价格快照 | 日期、供货价、渠道售价、税费口径、人数、间数、规则版本及明细 |
| 政策快照 | 预订/入住限制、早餐、取消阶梯、免费取消截止、支付类型及来源版本 |
| 入住人/联系人 | 供应所需姓名、人数、手机号及必要证件信息；按需采集、脱敏展示 |
| 取消/退款请求 | 请求方、原因、政策计算、预计及实际金额、供应处理、资金处理、幂等号 |
| 状态审计 | 状态前后、触发事件、操作者、来源、时间、关联请求/事件 |

酒店主来源切换、规则调整、映射纠错均不改写已创建订单的快照和履约身份。

### 9.3 状态边界

分别维护支付状态、供应履约状态、入住状态、取消状态和退款状态；主订单状态由这些事实按规则聚合，不将 PAID 等同供应确认。

- 支付：未支付、处理中、已支付、失败/关闭。
- 履约：未提交、预占中、预占成功、提交中、待确认PENDING_CONFIRM、已确认CONFIRMED、明确失败FAILED、结果未知UNKNOWN。模式INSTANT/ASYNC与这些运行状态分开记录。
- 入住：未到店、入住、离店、未到店等；来源于供应反馈或受权操作。
- 取消：未申请、申请中、取消成功、拒绝、结果未知。
- 退款：无退款、待退款、处理中、成功、失败；真实退款接口未接通时不得模拟成资金已退。

状态更新采用预期状态/版本条件并检查影响行数；渠道回调、支付回调和补偿任务不得全量覆盖订单旧快照。支付与取消并发时只能产生一条合法结果路径，远端已成功但本地失败必须由持久化恢复任务处理。

### 9.4 渠道通知方向调整

当前存在主动 pushOrder 及 MOCK/YESTE 演示语义。目标主线改为“渠道来单 → 平台向供应商履约 → 平台向渠道通知结果”。

渠道适配器按实际协议区分商品/价库分发、订单接入、状态通知；不把订单确认一律当成向渠道新建订单。旧 push 接口先盘点调用方，必要时隔离为明确能力。占位适配器仅允许演示环境，真实环境不可返回虚拟成功。

## 10. 权限与现有 merchant 模型迁移

### 10.1 权限要求

- 平台操作人员通过角色权限管理配置、映射审核、跨渠道排查及供应对账。
- 渠道只能访问本渠道订单和已授权商品，不能看到采购价、其他渠道价格/身份及供应凭据。
- 供应商 API 调用使用独立凭据；如需供应商人员门户，作为后续需求，不默认创建多租户系统。
- 订单详情、支付/取消等入口必须校验调用主体与订单关系；随机订单 ID 不作为授权机制。
- 网关清理外部伪造身份头；内部端点不经公共路由暴露，并通过网络边界与服务身份验证保护。

### 10.2 merchant 处理

1. 盘点 merchant 表、账号、角色、merchant_id 引用、Feign 接口、Gateway 路由、监控与演示数据。
2. 将账号逐项分类：平台员工、渠道接入账号、演示账号或无法识别账号。
3. 角色按目标用途迁移；无法判定的停留待处理，不自动赋平台权限。
4. 存量订单按外部单号、来源、历史映射补渠道和供应商；无法证明的标记“来源待核实”，不批量填 MOCK 或默认渠道。
5. 新订单改为记录 channel/partner；兼容期保留 merchant_id 作为历史字段，不再用于新业务授权。
6. 验证全部调用迁移后再停用 merchant 路由/服务；删除表和历史数据不属于本期自动动作。

AGENTS 中现有商家路径/隔离规则在相关代码退役前仍需遵守。正式实施时同步更新项目规则、接口文档、端口登记及监控，避免出现新旧模型同时生效的歧义。

## 11. 可靠性、缓存与运行配置

| 项目 | 需求 |
| --- | --- |
| Outbox | 订单事务内写事件；修复重试计数语义；多实例领取/租约；退避、失败告警、人工重放 |
| 消费幂等 | 持久化事件 ID 和处理结果；幂等记录与本地副作用同事务；外部副作用按请求号查证 |

| 远端操作 | 供应预订、取消、退款等均有独立尝试记录；未知结果先查证；任务有 next_retry_at 与终止/人工处理状态 |
| 库存原子性 | 按库存池和订单操作幂等；版本/条件更新；不以聚合 frozen 数量代替订单归属 |
| 缓存 | Key 含渠道、来源、计划、日期及必要人数维度；L1 多实例失效；映射/规则版本变化停用旧报价 |
| 缓存写时机 | 事务提交后失效；失败清理可追踪重试；报价提交必须再次校验权威状态 |

| 配置 | 密钥外置、凭据脱敏、生产日志级别与采样可配置；按渠道配置 CORS |
| 可观测性 | 关联平台单号、渠道外单号、供应请求号、事件 ID、traceId；日志不记录完整入住敏感资料 |

## 13. 数据迁移与切换

### 13.1 迁移步骤

1. 只读核对运行库与仓库 SQL，输出实际列、索引、缺失字段、重复业务键及历史数据数量。
2. 增量创建来源、映射、计划、快照、操作记录等对象；不重跑全量初始化脚本覆盖数据。
3. 为已有 hotel/room_type 建立来源记录；原始供应编码保留，平台 ID 不变。
4. 建立旧集团码、供应商、渠道及 merchant 的显式转换表；歧义进入待处理清单。
5. 将历史价库迁入指定旧来源和 LEGACY 计划；未确认前不宣称其为真实 BAR 计划。
6. 历史订单保留原金额、状态、单号；缺失资料标记未知，不能用现价伪造历史成交快照。
7. 新查询影子运行，比对酒店、价格、权限及可售范围；按渠道灰度启用新报价和新单。
8. 新订单按模型版本分流，老订单继续走原履约身份；切换后停止旧链路接收新单。

### 13.2 切换与回滚要求

- 每阶段记录回填数量、失败原因及核对结果，迁移脚本可重入且有检查点。
- 不依赖跨库外键维持业务正确；本地唯一约束与服务校验结合。
- 回滚优先关闭新单入口/切回查询版本，不撤销已经发到供应商的真实订单。
- 已成交的新模型订单必须保留可处理路径；代码回滚前验证兼容性，不能直接切到无法识别这些订单的旧版本。
- 演练数据、占位单号及真实业务数据区分，不能自动迁成真实履约成功。

## 14. 分阶段交付与验收

| 阶段 | 交付内容 | 进入下一阶段条件 |
| --- | --- | --- |
| 第一阶段：主体与静态模型 | 编号字典、供应商能力、来源快照、稳定平台酒店及人工映射 | 集团/第三方来源隔离，主来源切换不换平台 ID，审计完整 |
| 第二阶段：匹配与房型 | 标准化、候选评分、审核、房型映射、误关联撤销 | 标注样本验收通过；自动关联未达标保持关闭 |
| 第三阶段：报价与规则 | 多计划、多来源、共享库存、渠道授权、报价凭证 | 同计划报价与下单一致，无跨渠道泄漏及重复放量 |
| 第四阶段：订单与恢复 | 渠道来单、快照、供应履约、取消/退款记录、Outbox/补偿 | 并发、超时、重放及恢复测试通过，真实供应适配单独验收 |
| 第五阶段：迁移与收口 | 数据回填、灰度、merchant 退役准备、文档监控同步 | 来源可追溯、权限核对通过、回滚演练完成 |

### 14.1 关键验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| 静态-01 | 同酒店先第三方后集团同步 | 平台酒店 ID 不变，审核/确认后以集团为主，第三方报价保留 |
| 静态-02 | 名称相似但城市或门牌冲突 | 不自动合并，显示冲突依据 |
| 静态-03 | 同品牌相邻两店、统一客服电话 | 电话与品牌不能单独触发自动关联 |
| 静态-04 | 来源城市编码不同、坐标系不同 | 标准化后比较；缺少转换依据时不生成虚假高置信度 |
| 静态-05 | 集团同步失败、字段为空 | 不清空已发布有效资料；补齐策略与来源可见 |
| 静态-06 | 解除误关联且存在历史订单 | 历史快照和履约不变，新报价按映射新版本生成 |
| 价库-01 | 同来源同房型同日双早/无早计划 | 两份报价独立保留，权益明确 |
| 价库-02 | 多计划共享一个库存池 | 并发下单不重复放量，操作按订单幂等 |
| 价库-03 | 两供应商同名价格码 | 规则及报价互不串用 |
| 价库-04 | 多晚某晚缺价、过期或币种不同 | 该方案不可下单，不拼接来源补齐 |
| 渠道-01 | 未授权渠道查询或伪造渠道编码 | 拒绝或不返回商品；不能改变认证身份 |
| 渠道-02 | 只有渠道级加价而无授权 | 不可售 |
| 渠道-03 | 计价依赖异常 | 不按零加价成交，返回可追踪的不可用结果 |
| 订单-01 | 展示、报价、下单相同有效条件 | 逐日金额和总价一致，政策与来源有快照 |
| 订单-02 | 同渠道外单号重复/并发创建 | 同内容返回同单，不同内容明确冲突 |
| 订单-03 | 不同渠道查询/取消同一订单 | 仅所属渠道或授权平台人员成功 |
| 订单-04 | 供应已接单但请求超时 | 标记未知并查证，不重复落单或自动换供 |
| 订单-05 | 支付和取消并发、远端成功本地失败 | 状态合法且能恢复，无永久库存/金额悬挂 |
| 订单-06 | 政策发布后取消旧订单 | 依据旧订单快照计算，保留申请与实际结果 |
| 订单-07 | 即时确认返回明确成功/拒绝，或调用超时 | 分别为已确认、明确失败、结果未知；超时不重复下单 |
| 订单-08 | 异步下单已受理，供应商稍后确认或拒绝 | 首次返回待确认；最终结果经回调/查单推进并可靠通知渠道 |
| 订单-09 | 异步回调早到、重复或与查单并发 | 能关联既存请求，同一结果只生效一次，不回退终态 |
| 订单-10 | 待确认超时或取消期间收到迟到确认 | 不自动认定失败/恢复订单，进入查证或取消补偿；配额不提前错误释放 |
| 消息-01 | 多实例扫描、ACK 超时、重复消费 | 不重复产生外部订单；失败可重放，计数正确 |
| 迁移-01 | 无法证明历史渠道/供应关系 | 标记待核实，不默认迁给某渠道 |
| 缓存-01 | 两实例下发布新规则或解除映射 | 旧缓存不允许继续生成可成交错误报价 |

### 14.2 性能与质量验收方法

- 使用脱敏标注数据覆盖别名、旧名、缺地址、邻近分店、坐标偏移等类别，分别统计自动关联精确率、覆盖率及人工处理量。
- 自动关联门槛建议为评审样本零误合并；上线小批量抽查和人工撤销能力必须先具备，不能把样本结果当作全量正确保证。
- 同步、匹配、报价、订单分别建立吞吐和延迟基线；数据规模及目标并发确认后设定数值指标，不以未经测量的毫秒数作为承诺。
- 报价查询与订单提交压测包括多渠道、多计划和库存热点，观察数据库锁、Redis、线程池及补偿积压。

## 15. 待确认项与建议默认值

以下不阻碍需求评审，但涉及真实业务的实现应在对应阶段前确认。

| 待确认项 | 建议默认值 |
| --- | --- |
| 两种确认模式下的收款、核销、最长待确认时间和取消承诺 | 按供应合同及渠道协议分别确定；未明确前不将现有30分钟配额超时用于真实异步订单 |
| 集团缺失字段能否用第三方补齐 | 允许补齐非冲突展示字段，必须记录来源；政策和履约信息不从静态补齐 |
| 供应报价是实时库存还是平台配额 | 按供应商/合同配置；未知来源禁止按平台独立配额开放 |
| 渠道订单由谁收款、何时向供应商确认 | 演示保留 PP；真实渠道按合同确认，未定义前不开放真实成交 |
| 第三方静态可信度与集团归属证明 | 维护来源等级与证据，不按单个 partner_type 盲目认定所有记录权威 |
| 自动关联阈值与审批策略 | 初期只推荐，人工确认；标注校准后再启自动关联 |
| 现付、包价、小时房及完整财务结算 | 后续专项，不以默认 PP 流程代替 |
| 是否存在真实对外主动推订单协议 | 无证据则不作为主流程；有则按明确渠道能力独立保留 |

## 16. 完成标准

完成不仅是加表和接口：主体语义、来源追溯、酒店/房型映射、报价与订单闭环、权限隔离、失败恢复、迁移检查及监控文档必须共同通过验收。未接真实供应商或资金系统的能力必须明确标为演示/未接入，不以占位成功证明业务闭环。
