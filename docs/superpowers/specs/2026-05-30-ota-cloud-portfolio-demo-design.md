# OTA Cloud 作品展示 Demo 设计

日期：2026-05-30

## 目标

在 `ota-cloud` 里插入一个可视化展示章，先暂定为 **第 8.5 章：作品展示 Demo**。

这个页面不是内部管理后台，也不是面试简历页，而是面向程序员客栈这类兼职平台的 **单个项目案例页**：

- 要有真实 URL 可以访问。
- 要适合截图放到平台主页或项目相册。
- 要让潜在客户快速相信：这个项目是完整交付过的系统，不是静态玩具页面。
- 要能展示 OTA Cloud 的业务能力和技术深度，但不暴露后台账号、Token、数据库密码等敏感信息。

## 受众

主要受众：

- 在兼职平台浏览个人主页的潜在客户。
- 平台审核人员或想快速判断交付能力的访客。

次要受众：

- 有技术背景的访客，他们会关心这个项目是否真的有后端、消息、缓存、部署和验证证据。

## 页面定位

页面展示的是 **OTA Cloud 酒店预订微服务平台**，重点证明以下能力：

- Gateway + Auth/User 的登录鉴权链路。
- 酒店内容与房型/价库查询。
- 订单创建、支付、取消，以及库存冻结、扣减、释放。
- Kafka Outbox 可靠事件投递。
- Redis、MySQL、Nacos、Kafka、Docker 真实环境部署。
- 第 8 章 focused tests 和真实 smoke test 验证结果。

这个插入章不重新打开第 8 章回归测试，也不提前进入第 9 章供应适配。

## 页面策略

采用已确认的 **混合型项目案例页**：

- 有案例说明，让客户知道你交付了什么。
- 有产品化界面，让截图看起来像真实系统。
- 有技术证明，让懂技术的人看出后端深度。
- 做成静态站，方便部署到 GitHub Pages、Vercel、Netlify 或其他静态托管平台。

公开页面默认不连接真实后台做写操作，避免任何访客直接修改 Windows Docker 里的订单和库存。

## 数据模式

使用安全的静态优先模式：

- 页面默认使用脱敏展示数据。
- 展示最近真实 smoke test 证据，证明系统真实跑通过：
  - 支付链路订单：`5ee51f19135444f890823514693f8513`，状态 `PAID`，`order-paid SENT`。
  - 取消链路订单：`9aeae2449e534d98ae542ddd3f2d197b`，状态 `CANCELLED`，`order-cancelled SENT`。
  - 2026-05-30，房型 `D` 库存证据：`available=18`、`frozen=0`、`booked=2`。
- 链路演示采用前端交互回放，模拟状态变化，不直接写真实数据库。

公开页面第一版不做 Live Backend 调用。后续如果需要现场演示真实链路，可以单独加受保护的 Live Mode，但不能默认开放给所有访客。

## 信息架构

### 1. 首屏和产品预览

首屏要在第一眼说明：

- 项目名：OTA Cloud 酒店预订微服务平台。
- 一句话价值：一个可部署的酒店预订后端系统，覆盖订单、库存、缓存、网关和可靠消息。
- 技术栈标签：Spring Boot 3、Spring Cloud、Nacos、Kafka、Redis、MySQL、Docker。
- 主要入口：
  - 查看链路演示。
  - 查看架构拓扑。
  - 查看验证证据。
- 右侧或下方露出产品预览：订单状态、库存状态、Outbox 状态、服务健康状态。

首屏要像一个真实交付项目，而不是只有口号的营销页。

### 2. 业务大屏区

这一块要适合截图，展示客户能看懂的业务结果：

- 订单数量。
- 支付金额。
- 可用库存。
- Outbox 投递状态。
- 服务状态汇总。

目的：让非技术客户也能看出系统在做什么。

### 3. 交互链路回放区

提供前端模拟回放，不写真实后端：

- 登录。
- 查询酒店/价库。
- 创建订单。
- 支付订单，并展示库存扣减和 `order-paid SENT`。
- 取消订单，并展示库存释放和 `order-cancelled SENT`。

页面状态需要清晰展示：

- 当前步骤。
- 请求/响应摘要。
- 订单状态。
- 库存计数。
- Outbox 事件状态。

目的：让客户点击几下就能理解“下单系统是怎么跑起来的”。

### 4. 架构拓扑区

展示系统结构：

- Gateway 作为统一入口。
- Auth/User 负责登录鉴权和用户信息。
- Hotel 负责酒店/房型内容和缓存。
- Inventory 负责价库、库存和状态变化。
- Order 负责订单状态机和 Outbox 写入。
- Kafka 接收 `order-paid` 和 `order-cancelled`。
- MySQL 存业务数据。
- Redis 支撑缓存和 Token 黑名单。
- Nacos 负责服务发现和配置。

这块要做到：非技术客户能看懂大概流程，技术访客能看出微服务能力。

### 5. 交付能力区

用客户能理解的语言总结可交付能力：

- 微服务后端设计。
- 订单与库存领域建模。
- 可靠异步消息投递。
- 缓存与服务发现。
- Docker 真实环境部署。
- 回归测试和真实链路验证。

避免堆术语，要把技术能力转成“能交付什么”。

### 6. 验证证据区

展示第 8 章最终证据：

- Maven focused tests：
  - Gateway/Auth/User：13 个测试通过。
  - Hotel/Inventory/AI：18 个测试通过。
  - Order：12 个测试通过。
- 真实 smoke 脚本：
  - `scripts/chapter8-real-smoke.sh`
- 支付链路证据：
  - 订单 `5ee51f19135444f890823514693f8513`，`PAID`，`order-paid SENT`。
- 取消链路证据：
  - 订单 `9aeae2449e534d98ae542ddd3f2d197b`，`CANCELLED`，`order-cancelled SENT`。

不要展示后台密码、SSH 密码、数据库密码、完整连接串或任何真实密钥。

## 技术方案

在仓库里新增一个独立静态前端应用，推荐目录：

```text
ota-portfolio-demo/
```

推荐技术栈：

- Vite
- React
- TypeScript
- 普通 CSS 或 CSS Modules

数据放在前端静态配置里：

- 指标数据。
- smoke test 证据。
- 架构节点和连线。
- 链路回放步骤。

这个应用不打包进现有 Spring Boot 服务，避免影响第 1-8 章主线，也方便部署到静态托管平台。

## 视觉要求

- 风格要专业，偏 SaaS/项目交付案例，不做花哨个人主页。
- 首屏必须出现项目本体和系统证明，不要做空泛 Hero。
- 配色不能单一，要用稳重底色 + 清晰状态色区分健康、告警、已支付、已取消、已投递。
- 卡片、网格、按钮和状态标签要尺寸稳定，适合截图。
- 桌面端截图优先，移动端保持可读即可。
- 文案要面向客户，少写内部教程口吻。

## 安全与隐私

- 前端源码里不能放真实 admin 密码。
- 不能放 Token、数据库密码、SSH 密码、Nacos/Kafka/MySQL 连接密钥。
- 公开页面不能直接写真实订单或库存。
- smoke 订单 ID 可以展示，因为它们已经记录在项目进度文档中，且不属于密钥。
- 如果以后加 Live Mode，必须和公开静态页面隔离，并加保护。

## 不做的事

本章不做：

- 第 9 章供应适配。
- 真实在线支付。
- 公网访客直接登录 Windows Docker 后台。
- 暴露 Nacos、Kafka、MySQL 控制台或凭据。
- 做完整个人作品主页或多项目主页。

## 完成标准

- 页面可以作为静态站部署，形成真实可访问 URL。
- 页面能清楚展示 OTA Cloud 是一个完整酒店预订微服务项目。
- 首屏、业务大屏、链路回放、架构拓扑都适合截图。
- 交互回放能展示支付和取消两条链路，不写真实后端。
- 页面能展示第 8 章 smoke test 证据，且不泄露敏感信息。
