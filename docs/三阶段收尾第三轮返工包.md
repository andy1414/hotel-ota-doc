## 二、任务一：权威取消事实结构化（P1，阻断）

### 当前问题

`BookingFlowService.applyInbox` 用 `reason.contains` 判断原取消结果，说明文本还拼接供应自由文案，可能同时包含两种标记或因措辞变化丢失标记。冲突分支还可据此调用库存取消及启动退款，与“冲突证据本身不触发成功副作用”的要求不一致。

重点模块：`ota-common` 交易契约、`ota-supplier` 事实合并与投递、`ota-order` 收件箱与状态推进、相关 Mapper XML、初始化 SQL、测试结构和接口文档。

### 必须实现

1. 删除依赖中文说明、自由文本或事件 ID 前缀判断权威状态的业务分支。`reason` 仅用于展示和诊断，改变它不得改变资金库存行为。
2. 权威取消事实应有结构化状态和原事件身份，绑定订单、供应商、供应请求及适用的取消请求。明确事实与矛盾证据分别持久化；校验错归属、缺失、非法组合及同号内容变化。
3. 推荐将原事实作为独立事件收敛，冲突事件只记录矛盾并转人工复核。冲突先到且原事实尚未核实时，保持现有库存和资金，等待可信原事实，不根据说明猜测，也不无限静默挂起。
4. 若采用包含原事实的复合事件，必须在契约中明确原事实字段、来源和校验规则，并分开“执行经校验的原事实”与“记录冲突证据”；不得仅为兼容现有测试保留隐式文本逻辑。同步更新需求和接口文档供复核。
5. 原拒绝不退款、不归还配额；原成功可按既有流程执行一次取消和退款。后到矛盾不撤销已执行事实，不重复操作；始终可追溯原事实及矛盾。
6. 覆盖同步取消返回、异步回调、查询恢复、前序 ACK、重试和多实例，不只修复 inbox 单一入口。前序 ACK 的接收/处理语义须明确。
7. SQL 在 XML；本地事务不跨网络调用。契约、校验、数据库和测试结构同步更新，TEST 调试接口保持受保护。

### 必交验证

用真实 XML/事务及可控屏障验证：冲突先到、原事实先到、RPC 与回调交错、首投失败重试、重复投递和服务重建。新增说明为空、任意改写、同时含两种标记、错误原事件身份、错误取消请求和非法结构组合用例。

每项检查原事实持久化、订单状态、库存数量、退款笔数、供应调用次数。相同结构化事实配不同文案必须产生相同业务结果；只有冲突证据且无可信原事实时不得产生取消成功副作用。保留前两轮有效并发回归。

## 三、任务二：通知验收绑定稳定版本（P2，验收阻断）

### 当前问题

`booking-flow-smoke.py` 将收到错误 ACK 的某条事件固定为等待对象，但该事件可能属于付款前版本。真实渠道收到新版本后可将旧事件标为 `SUPERSEDED`，旧事件不会再变为 `DELIVERED` 或 `DEAD`；自包含模拟服务未覆盖此行为。

### 必须实现

1. 在建单前注册故障规则，完成必要订单状态变更后明确目标稳定版本，按订单 ID、版本和事件 ID 关联错误 ACK、尝试次数、终态及审计。
2. 选择方案并写明：只对稳定目标版本执行故障验收，或显式处理合法版本替换并重新绑定稳定事件。不得把 `SUPERSEDED` 当送达成功，不得通过跳过死信步骤消除超时。
3. 证明目标版本实际返回过错误 ACK，未被记成功；恢复后该版本正确 ACK 成功。死信场景必须对稳定事件验证耗尽、授权重放、未授权拒绝、审计和最终送达。
4. 真实 Java 渠道增加“旧版本错误 ACK 后新版本到达”测试，自包含模拟服务应实现与验证目标有关的版本游标和替代行为，防止模拟通过而真实环境挂起。
5. 版本持续变化、目标永不到达、始终错误 ACK、重放失败、接收器异常都应有界失败并非零退出；条件等待不能替换成固定 sleep。错误 ACK 测试结束后，新版本语义与通知租约保护不回退。
6. 默认运行遵从部署网络配置；本地自包含验收明确回环地址应直连。仅为本次命令配置 `NO_PROXY/no_proxy` 或显式本地传输，不修改用户全局代理，不将代理超时归类为业务失败。

交付脚本断言、真实 Java 测试、模拟版本替换测试及负向退出结果；区分 order→channel 接收与 channel→外部渠道投递。
