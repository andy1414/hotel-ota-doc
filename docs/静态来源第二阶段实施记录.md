# 静态来源第二阶段实施记录

日期：2026-10-29。继续第一阶段，交付来源审核纠错与来源房型映射的内部业务接口；不代表完整需求设计全部完成。

## 本批完成范围

### 酒店来源审核

- 支持按供应商/未关联状态检索来源酒店，使用ID游标分页，每页最多100条。
- 基于真实来源快照生成候选，名称、地址、地理距离、电话及品牌使用共用评分引擎；老admin候选入口复用同一引擎，不再维护两套算法。
- 同城市每次最多扫描200间平台酒店，返回nextHotelId/hasMore，调用方须继续扫描至hasMore=false；不会将单批无结果误报为全城无结果。
- 候选保存来源版本、双方快照、目标指纹、评分依据和算法版本。同来源版本/目标指纹的候选重复生成不覆盖拒绝或确认决定。
- 支持确认、拒绝、审核历史查询。确认前校验最新来源版本和目标指纹；旧资料审核结果不能静默作用于新资料。
- 确认只改变映射，不自动发布。人工直接确认入口同样要求来源版本、目标指纹、操作者和原因。
- 非主来源可单独解除，不改变已发布酒店。当前主来源解除必须显式提交已确认的替代来源ID及版本，在同一事务中先发布替代，再撤销旧关联。
- 剩余有效集团来源优先，不能借替代参数越过集团来源改用第三方。不能指定另一间酒店的来源作为替代。
- 撤销后原确认候选不会自动恢复关联；需重新审核。原订单、库存和供应商侧订单不参与映射纠错。
- 全部审核和纠错记录操作者、原因、来源版本、关联前后平台酒店及候选编号。

### 房型来源与人工映射

- 来源房型以酒店来源ID+供应原始房型编号唯一定位，保留独立版本和静态快照。
- 静态属性参考api_hotel.txt的room_type，首批包含名称、入住人数、床数量、床型、窗户及面积；早餐和取消政策留给价格计划。
- 酒店来源未确认时只能保存原始房型，不能确认到平台房型。
- 返回该平台酒店下的房型审核目标、目标指纹和属性冲突；保守要求关键属性等价。面积字符串口径不同先标准化，不自动假定面积范围等价。
- 确认时核查酒店来源版本、房型来源版本、目标指纹、目标有效状态和酒店归属；名称相似不能替代关键属性证据。
- 同一来源房型不能直接搬迁到另一平台房型；必须显式解除、修改快照后重新核实。
- 房型确认/解除有审计。酒店来源解除时，同一事务记录并清理其全部房型映射，防止纠错后把旧房型带到新酒店。
- 不覆盖平台房型，不创建价格计划，不修改库存，不重写历史订单快照。

## 数据库升级要求

本批新增：

1. `init-sql/006-hotel-source-review.sql`：候选快照、拒绝负样本及酒店来源审核流水。
2. `init-sql/007-room-type-source.sql`：来源房型与房型审核流水。

启用本批代码前必须按005→006→007顺序完成数据库核对和迁移。尤其酒店来源解除现已包含房型映射级联清理，不能只部署006而缺少007。

功能仍由HOTEL_SOURCES_ENABLED控制，默认关闭；全部新增入口仍要求HOTEL_SOURCES_INTERNAL_TOKEN。不自动执行远端SQL、不回填来源关系、不启用真实同步或发布。

## 内部接口补充

统一前缀 `/internal/hotel-sources`，必须提供 `X-OTA-Internal-Token`。

| 方法/路径 | 用途 |
| --- | --- |
| GET `/` | 来源检索；partnerCode/unmappedOnly/afterId/limit |
| POST `/{id}/candidates/generate` | 分页生成候选；afterHotelId为平台酒店扫描游标 |
| GET `/{id}/candidates` | 当前来源版本的候选及决定，afterId/limit分页 |
| GET `/{id}/reviews` | 审核历史，afterId/limit分页 |
| POST `/candidates/{id}/confirm` | 按候选确认；sourceVersion/operator/reason |
| POST `/candidates/{id}/reject` | 拒绝候选；sourceVersion/operator/reason |
| POST `/{id}/revoke` | 解除酒店来源；sourceVersion/hotelId/operator/reason，主来源还需replacementSourceId/replacementSourceVersion |
| POST `/{id}/rooms` | 同步来源房型；sourceRoomCode/sourceVersion/data |
| GET `/{id}/rooms` | 来源房型列表，afterId/limit分页 |
| GET `/rooms/{id}/targets` | 房型审核目标、版本、指纹与冲突 |
| POST `/rooms/{id}/confirm` | 确认房型；roomTypeId/hotelSourceVersion/sourceVersion/roomFingerprint/operator/reason |
| POST `/rooms/{id}/revoke` | 解除房型；hotelSourceVersion/sourceVersion/operator/reason |

兼容说明：第一阶段直接确认 `POST /{id}/confirm` 新增必填sourceVersion、hotelFingerprint和reason。该接口不是公开渠道协议；调用方应改走持久化候选确认，或传入审核看到的指纹。第一阶段的双字段确认不再接受。

## 并发与事务

- 审核及房型写操作按供应商→平台酒店→来源行的顺序加锁，关键检查使用最新锁定读。
- READ_COMMITTED避免审核先普通读取、等待互斥锁后仍读取旧事务快照。
- 候选决定条件更新、唯一索引、映射确认条件更新共同保护幂等和并发决定。
- 来源解除、替代静态发布、房型映射清理和审计同事务；异常整体回滚，缓存只在提交后失效。

## 验证与后续

回归覆盖版本过期、指纹变化、拒绝重试、确认后解除、分批候选扫描、替代来源越界、房型跨酒店、关键属性缺失及父映射清理；Mapper XML有实际解析和参数绑定检查。

未执行真实MySQL迁移和多连接锁竞争验证，单元测试不代替这些检查。尚未交付管理前端、行政区自动映射、坐标系转换、酒店合并拆分、人工字段锁定和自动关联放量。

下一批重点是价格计划、共享库存、渠道授权及报价凭证，并把已确认的酒店/房型来源映射接入统一报价，保持静态来源与履约来源分离。
