# 三阶段收尾返工包

日期：2026-10-30  
用途：交给实施人员执行；本包不代表返工已经完成。

## 一、返工依据与边界

依据：[收尾复核文档](三阶段收尾复核文档.md)第九节、[修改需求](三阶段收尾修改需求.md)、[接口契约](交易接口契约.md)。复核曾记录六个交易相关模块 287 项通过，但仍存在取消终态覆盖竞态和实际 HTTP 联调证据不足。该数量是历史基线，不能作为返工后的验收结果。

接手时先检查当前工作区：缺陷可能已有后续修改，必须验证最终源码，不重复覆盖有效修复。保留现有未提交改动，不重置工作区，不擅自提交或推送。

核心主体为平台、供应商、渠道；不恢复商家租户。测试数据不做迁移或兼容回填，不自动清空远端数据库。真实外部机构接入不属于本次返工；未配置时仍返回未配置或不可用。

## 二、任务一：取消结果统一收敛（阻断项）

### 触发场景

外部取消调用尚未返回，异步回调先提交 `CANCEL_REJECTED`；同步调用随后返回 `UNKNOWN` 或 `CANCELLED`。原 `finishCancel` 无条件回写可能覆盖已持久化结果。反向顺序也必须验证。

重点文件：

- `ota-supplier/src/main/java/com/ota/cloud/supplier/booking/SupplierBookingStore.java`：`process`、`beginCancel`、`finishCancel`。
- `ota-supplier/src/main/resources/mapper/SupplierBookingMapper.xml`：取消记录锁定和结果更新。
- `ota-supplier/src/test/java/com/ota/cloud/supplier/booking/SupplierBookingDatabaseTest.java`。
- `ota-order/src/main/java/com/ota/cloud/order/booking/BookingFlowService.java` 及 `BookingFlowDatabaseTest`：冲突结果处理和资金库存保护。

行号可能随工作区变化，以符号和最终源码为准。

### 必须满足的状态规则

| 已持久化取消结果 | 新到结果 | 必须行为 |
| --- | --- | --- |
| 无明确结果 / UNKNOWN | UNKNOWN | 保持待查证，不释放配额、不退款 |
| 无明确结果 / UNKNOWN | 明确拒绝 | 保存拒绝，保留有效预订及配额 |
| 无明确结果 / UNKNOWN | 明确取消成功 | 保存成功，按既有订单流程确认取消及退款 |
| 明确拒绝或取消成功 | UNKNOWN | 保留原明确结果，不降级、不覆盖 |
| 明确拒绝 | 同义拒绝 | 幂等，不新增业务副作用 |
| 明确取消成功 | 同义取消成功 | 幂等，不重复释放或退款 |
| 明确拒绝 | 明确取消成功 | 保留原事实，记录矛盾并通知订单进入人工复核 |
| 明确取消成功 | 明确拒绝 | 保留原事实，记录矛盾并通知订单进入人工复核；不撤销已经发生的资金库存事实 |

同步返回与异步回调必须共用同一套规则，不能只修复一个入口。结果合并在本地事务中完成，锁顺序一致；仅加锁而不比较已有结果不能解决后写覆盖。业务 SQL 保留在 Mapper XML。

取消操作结果与供应预订状态分别保存。拒绝取消不等于预订失败；矛盾证据不得丢弃。重复请求应返回当前已收敛事实；同号内容不同冲突，拒绝后换号自动取消继续禁止。当前不开放多轮自动取消，不引入无法关联尝试身份的新行为。

### 测试交付

使用可控阻塞适配器和同步屏障，不用固定 sleep 碰运气。实际执行独立事务和真实 Mapper XML：外部调用挂起 → 回调提交 → 释放调用 → 检查数据库与订单。至少覆盖拒绝/成功/未知的双向顺序、重复事件、服务对象重建后的重试、不同取消号及内容冲突。

每个关键用例断言：取消记录最终值、供应预订状态、订单是否进入复核、适配器调用次数、事件投递、已用/可用配额与退款笔数。模块替身无法证明跨服务副作用时，补充订单侧测试或 HTTP 场景，不以供应侧状态断言代替。

## 三、任务二：补齐跨服务验收（验收阻断项）

在明确指定的独立测试环境执行，使用现有 `scripts/reset-booking-test-data.py` 和 `scripts/booking-flow-smoke.py`。先干跑，再核对实际目标连接；实际重建必须显式执行，禁止默认清理远端库。所有服务和脚本使用同一份测试配置，密钥不进代码和日志。

现有正常闭环必须真实执行；补充下列可重复的故障场景：

1. 即时确认、异步待确认及签名重复回调、支付、取消退款、最终通知 ACK。
2. 相同外部单号重试与内容冲突，供应外部下单只有一次。
3. 取消明确拒绝后保持预订、配额和资金；重试及换号不新增取消调用。
4. 提交超时未知，按原请求号查证恢复；查证完成前不释放配额、不盲目重下。
5. 通知失败后恢复、错误 ACK、重试耗尽与人工重放；记录版本及事件身份。
6. 本任务一的取消回调与同步返回竞态；如 HTTP 环境无法精确调度，保留真实事务专项测试证据，并明确 HTTP 覆盖边界。

需要新增故障控制时，仅使用显式 TEST 配置和受保护入口；不得开放生产无鉴权控制、伪造真实支付成功，或借故关闭签名和渠道隔离。

## 四、执行顺序

1. 核对当前修复基线及复现证据。
2. 修复取消结果合并，补充有效专项测试。
3. 依次完成模块回归；每次最多三个模块，只运行一个 Maven 进程。公共契约变更后先安装新 common，再测试依赖模块。
4. 执行实际 HTTP 正常与故障场景，记录证据。
5. 更新接口、验收记录和返工交付清单，交独立复核。

最终回归覆盖当前运行模块：common、gateway、auth、user、hotel、inventory、order、admin、ai、supplier、channel。父 POM 与 common 的安装先完成，再按最多三个模块分批执行；不得用 `-am` 隐含超出限制。归档 merchant 不计入运行模块验收。

## 五、交付清单与退出条件

- 修改文件与原因清单、最终差异标识；不得只给提交号而忽略未提交工作区。
- 专项测试名称、命令、运行时间、退出码与 Surefire 统计。
- HTTP 验收环境、场景、订单/请求/事件标识、最终状态与配额资金断言。
- 可长期保留的脱敏证据目录；`/tmp` 日志仅作临时路径。
- 尚未执行或失败的项目及原因，单列真实外部供应与资金机构未接入边界。
- 更新 [复核包](三阶段收尾复核包.md) 的交付填写区，但不自行把独立复核结论改为通过。

退出条件：两个阻断项均有关闭证据，必要回归无失败，独立复核可重现结果。环境不足时记录为待验证，不以文档或脚本准备完成替代联调完成。
