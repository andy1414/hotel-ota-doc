## 三、修改要求与验收条件

### 需求一：取消拒绝保持原有效订单

优先级：高。涉及 `ota-order`、`ota-supplier`、`ota-inventory`。

1. 供应明确拒绝取消后，取消状态为 `REJECTED`，保留有效供应预订、原资金事实和已占用配额，不退款、不归还已确认配额。
2. 同一取消请求号、相同内容重试应返回已持久化结果，不再次向供应发送取消；相同请求号内容变化应冲突。
3. 本期不开放拒绝后自动重新取消。不同取消请求号再次发起应明确冲突，并提示人工核实；订单入口和供应内部入口都需保护，不能只依赖上游调用纪律。
4. `SupplierResult` 结构化携带 `cancelRequestNo`、`priorState`、`priorEventId`（`reason` 仅用于展示与诊断，不得用于判断业务状态）；供应侧与订单侧分别持久化首次权威取消事实与后到矛盾证据。迟到的拒绝或取消回调若与取消请求号、原事件身份或既有状态矛盾，拒绝或隔离进入人工复核，冲突证据本身绝不触发配额释放或退款。
5. 超时或非确定结果保持待查证；恢复任务不能把未知或拒绝当作取消成功。矛盾结果进入人工复核，不能静默覆盖有效终态。

验收：同步拒绝、异步拒绝、重复及乱序回调、不同请求号、并发请求、服务重建后的重试均符合上述规则；断言真实供应适配器调用次数、库存数量及退款记录，而非只断言返回文案。

### 需求二：订单展示完全使用冻结快照

优先级：高。涉及 `ota-common`、`ota-inventory`、`ota-order`、`ota-channel`。

报价生成时冻结平台酒店 ID、平台房型 ID、酒店名称、房型名称、入住与离店日期、间数、入住人数、金额币种、确认模式和取消政策。建单、订单查询及渠道通知统一读取同一份冻结事实。

静态主来源、价库来源、实际履约供应商分别保存。集团静态优先只影响后续静态发布和新报价；不得更改历史订单酒店 ID、名称、价库或履约身份。确认模式只允许来自可信报价，渠道提交内容不得覆盖。

验收：生成报价后修改酒店名称或静态主来源，再建单及查询，订单仍使用原报价名称和身份；建单后修改房型、价格和政策，查询及通知仍保持原值。渠道视图不得泄漏采购价、供应凭据或原始内部快照。

### 需求三：付款期限与资金结果一致

优先级：高。涉及 `ota-order`。

`BEFORE_SUBMIT` 按已冻结渠道政策确定付款期限；`AFTER_CONFIRM` 在首次明确供应确认时起算，确认前不得因未付款提前到期。重复确认、事件重放和服务恢复均不得延长期限。资金成功和供应确认分别保存，只有两者满足才完成订单确认。

校验事件签名、渠道订单归属、金额和币种；交易号不得跨订单复用。同额不同小数位表示需按统一金额规则处理；真正冲突、重复收款、退款矛盾进入复核，不能覆盖原资金事实。

验收：覆盖两种付款时机、首次及重复确认、超时未知、重复资金事件、错金额币种、交易号复用和退款失败。使用可控时间验证起算点与截止值。

### 需求四：对账和渠道通知可查证

优先级：高。涉及 `ota-order`、`ota-supplier`、`ota-channel`。

对账同时展示本地状态、远端查证结果及差异。远端超时、未查明或响应归属错误不得展示为一致，也不得改写另一订单；应给出可识别的查证失败或未知结果。

渠道通知先持久化，再投递；保持订单版本及事件内容不可变。发送业务数据前复核事件租约、订单租约和最新版本；失去租约的工作线程不得继续发送。只有匹配事件号的有效 ACK 才算成功；失败执行有界重试，耗尽后可查询并人工重放，保留操作记录。

验收：覆盖超时、错误归属、旧版本、重复事件、ACK 错误、发送前租约过期及新版本抢占。通知地址安全校验、连接目标固定和禁止重定向的既有保护不得回退。

### 需求五：最终回归与跨服务验收

优先级：高。涉及所有当前运行模块、`init-sql`、`scripts` 和文档。

先完成最终源码的分批 Maven 回归，每次最多三个模块且只运行一个 Maven 进程；包括公共契约、真实 XML、数据库事务、控制器、网关鉴权及端口对账。已有通过记录不能替代最后修改后的测试。

在明确指定的独立测试库重建结构和种子，验证 Gateway → channel → order → inventory/supplier → order → channel 全链路。即时确认、异步确认、支付、取消退款、幂等重试及通知 ACK 都要有实际 HTTP 证据。网络超时等故障需通过可控 TEST 行为验证。

重建脚本默认干跑；实际执行必须明确目标测试库。脚本语法检查、H2 测试和真实跨服务联调分别记录，不混为同一类通过。
